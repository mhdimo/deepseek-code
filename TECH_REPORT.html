Abstract

This report presents the technical architecture of DeepSeek Code, a terminal-native AI coding agent that integrates large language model capabilities directly into the developer's command-line environment. Built on Bun, Ink (React for terminals), and a native C++ AI SDK, the system provides real-time streaming code assistance through a multi-agent orchestration framework with extensible tool execution. We describe the architectural decisions, component design, data flows, and implementation patterns that comprise this approximately 7,900-line TypeScript codebase spanning 72 source files, 19 built-in tools, and 3 specialized agent personas.

1 Introduction

DeepSeek Code is a terminal-based AI programming assistant that operates entirely within the developer's existing terminal workflow. Unlike web-based coding assistants or IDE plugins, it provides a native terminal experience with real-time streaming output, multi-step autonomous task execution, and interactive permission controls—all without leaving the command line.

The project was inspired by Claude Code's interaction model but is built with a fundamentally different architectural approach. While Claude Code uses a TypeScript-based agent loop via the Vercel AI SDK, DeepSeek Code leverages a native C++ engine (ai-sdk-cpp) for the core agentic loop, with TypeScript handling tool definitions, permission flow, and the terminal UI layer via Ink.

3.3 Session Management

A critical architectural pattern is that the C++ Session owns the authoritative conversation history, including memory injection and context compaction. The TypeScript messages[] state is a display copy. The session is cached globally (keyed by provider + model + workingDir + agent + memoryDir) and reused across turns, so history persists across multiple user messages within a session.

Session creation happens in agentSession.ts via getOrCreateMemorySession(). On first call for a given key, it constructs a C++ Agent with the model, tools, and system prompt—including auto-injected project context from CLAUDE.md, DEEP.md, or AGENTS.md. On subsequent calls with the same key, the cached session is returned with updated permission callbacks. The resetMemorySession() function drops the cache on /clear or provider/model switch.

Dual Type System Artifact. The codebase contains two nearly-identical type files: src/core/types.ts and src/types/index.ts. The latter is the more complete version (used by imports), while the former appears to be a stale artifact from the Vercel AI SDK to ai-sdk-cpp migration.

4 Tool System

4.1 Tool Interface & Factory

Tools are the fundamental abstraction for AI-accessible actions. Each tool implements the Tool<Input, Output> interface and is assembled via the buildTool() factory function in Tool.ts, which fills in safe defaults for optional properties:

PropertyDefaultDescription
isEnabled() => trueWhether tool is available in current environment
isConcurrencySafe() => falseCan run in parallel with other tools
isReadOnly() => falseWhether tool has side effects
checkPermissions{ approved: true }Default: always allow
userFacingNametool.nameDisplay name in the TUI
maxResultSizeChars100,000Max result size before truncation

4.2 Tool Registry & C++ Binding Adapter

The toolsToBindingFormat() function in tools.ts provides the critical bridge between TypeScript tools and the C++ engine. It:

  1. Converts Zod schemas to JSON Schema (removing $schema)
  2. Wraps each tool's checkPermissions() + call() in an async bridge function
  3. Handles abort signals via Promise.race() with an abort promise
  4. Calls onToolResult() callback for real-time TUI updates
  5. Enforces plan mode: if planMode is true and tool is not read-only, execution is blocked

The async bridge is the mechanism by which the C++ loop awaits JavaScript execution. When the model requests a tool call, the C++ engine invokes the bridge function, which runs the permission check and tool call in JavaScript (potentially blocking on user approval), then returns the result string to the C++ loop for context injection.

5 Multi-Agent System

DeepSeek Code defines three specialized agents in services/agent/index.ts, each with a distinct system prompt, permission set, and step limit:

AgentReadWriteExecuteMax StepsPurpose
Code ✓✓✓ 50 Full-access development agent. Implements features, debugs, runs tests, and executes shell commands.
Plan ✓✗✗ 15 Read-only analysis and planning. Explores codebases, identifies patterns, and produces actionable plans.
Review ✓✗✗ 15 Code review agent. Checks for bugs, security issues, performance concerns, and style violations.

Each agent's system prompt includes explicit instructions about autonomy, tool usage guidelines, and behavioral constraints. The Code agent, for example, is instructed to never ask "shall I continue?" but instead proceed autonomously—a design choice that emphasizes the agent's role as a proactive assistant rather than a passive tool.

The AgentManager singleton provides access to agent configurations and can instantiate Agent objects (the legacy path). The modern flow uses getOrCreateMemorySession() which creates a C++ Agent directly, bypassing the TypeScript AgentManager. Both paths coexist, with the legacy path serving as a fallback.

6 Streaming Query Engine

6.1 Event Architecture

The query() function in services/query.ts is the primary interface between the C++ engine and the TypeScript UI. It is an AsyncGenerator<QueryEvent> that iterates over the C++ session's sendStream() and maps native events to JavaScript types:

C++ EventQueryEvent TypePayload
text_deltatext-deltaStreaming text chunk
reasoning_deltathinking-deltaReasoning/rethinking text chunk
tool_call_starttool-call-startTool execution began (tool name, call ID)
tool_call_deltatool-call-deltaStreaming tool arguments (JSON partials)
tool_call_endtool-call-endTool arguments finalized
tool_resulttool-call-resultTool execution completed with result
step_finishstep-finishOne agent step completed
finishfinishGeneration complete (usage + cost)
errorerrorError occurred, terminates stream

6.2 Stream Processing in App.tsx

The processAgentStream() function in App.tsx consumes the event stream and updates React state. Key implementation details:

  • Ref-based mutable state: streamingTextRef, streamingThinkingRef, and streamingToolUseRef hold mutable values that accumulate across renders without triggering cascading re-renders.
  • Renderer yielding: yieldToRenderer() (setTimeout 0) is called between events to allow Ink's virtual DOM diffing to paint updates.
  • Step finalization: On tool-call-result, when all tool calls in a step are complete, the accumulated text + tool blocks are finalized into a Message appended to history. Streaming state then resets for the next agentic step.
  • Token tracking: The finish event carries cumulative token usage and cost estimates, updating the StatusBar display.

7.2 Permission Flow

Model requests tool call
  → tool.checkPermissions(input, context)
    → If agent permission ruleset denies: return denied immediately
    → If plan mode active and tool not read-only: block with message
    → If user approval needed: context.requestPermission()
      → App.tsx sets pendingPermission state
      → <PermissionPrompt> renders with diff/command preview
      → User: y/n/allow-all + optional Tab feedback
      → Promise resolves with decision
    → tool.call(input, context) executes
    → Result string returned to C++ loop

7.3 Interactive Feedback

A distinctive feature of the permission system is the ability for users to provide inline feedback. When the permission prompt appears, users can press Tab on the "Yes" or "No" option to enter amendment text. This feedback is embedded directly into the tool result as "💬 User note: ...", allowing the model to see and respond to the feedback immediately. This enables interactive refinement of tool operations without breaking the agentic flow.

Dangerously Skip Permissions. The --dangerously-skip-permissions CLI flag bypasses all permission prompts. This is intended for automated/CI workflows and is not recommended for interactive use.

8 Token Tracking & Context Management

8.1 Token Estimation & Pricing

The TokenTracker class accumulates token usage across steps and estimates costs using DeepSeek's published pricing:

ModelInput (/1M tok)Output (/1M tok)Cache Hit (/1M tok)
deepseek-chat$0.27$1.10$0.07
deepseek-reasoner$0.55$2.19$0.14

Cost estimation assumes a 70% cache hit rate on input tokens, which is conservative for multi-turn conversations where repeated context is common. Display formatting helpers produce human-readable strings like "1.2k tok" and "~$0.02".

8.2 Context Compaction

The ContextManager (in contextManager.ts) provides JavaScript-side context management as a fallback path. It uses a 1-token-4-characters heuristic and supports:

  • Token estimation: Rough calculation for messages, including thinking text and tool outputs
  • Auto-compaction: When usage exceeds 80% of the 64K context window, older messages are summarized into a synthetic system message, preserving the last N (default 6) messages intact
  • Tool output truncation: Tool results exceeding 4000 characters are truncated
  • Message preparation: Filters empty messages and limits to 30 messages for API calls
Note on Redundancy. The C++ engine's SlidingWindowStrategy handles context compaction natively. The JavaScript ContextManager is primarily relevant when using the legacy Agent class path rather than the modern C++ session path. Both layers coexist for robustness.

9.2 Key UI Features

Rich Markdown Rendering

The Markdown.tsx component is a zero-dependency markdown parser that implements: inline formatting (bold, italic, code, links), block elements (headings h1–h6, fenced code blocks, ordered/unordered lists, blockquotes, horizontal rules), and a special-char proximity lookup for fast plain-text skipping. Block parsing is memoized to avoid re-parsing on every render.

Inspection Mode

Activated via Ctrl+E, inspection mode allows navigating through all tool blocks across all messages with arrow keys. The selected block is highlighted with a "▶" indicator, and Space/Enter toggles expand/collapse of tool output. By default, the last tool block is selected, placing focus on the most recent execution.

Thinking Modes

The system supports two modes: off (normal generation) and whale (deep reasoning with deepseek-reasoner's extended thinking). Thinking text is rendered in dim italic with a "∴" prefix, collapsed by default. Users toggle with /think or Shift+Tab.

Command Picker

The slash command picker appears when the user types "/" and provides real-time fuzzy matching against 20+ commands. Commands are categorized (general, session, model, agent, MCP) with ranked matching (name → alias → description). Tab autocompletes usage templates; Enter executes immediately.

10 Configuration & Persistence

10.1 Layered Configuration

Configuration follows a layered merge pattern where later sources override earlier ones: 

DEFAULTS  ←  Config File  ←  Env Vars  ←  Persisted Settings  ←  CLI Args
   │              │               │               │                 │
deepseek     .deepseek-code    DEEPSEEK_*     settings.json      --model
--chat       ~/.config/        environment    ~/.deepseek-code/  --api-key
             ~/.deepseek-      variables      settings.json      --base-url
Figure 4: Configuration merge priority (later sources override).

Key features of the configuration system include:

  • Environment variable references: Config files support "env:VAR_NAME" strings that are resolved at load time, allowing secrets to stay out of config files
  • Named model profiles: Each profile specifies provider, model, API key, and base URL, switchable at runtime via /model <profile>
  • MCP server definitions: Servers with command, args, working directory, environment variables, and enabled/disabled state
  • Backward compatibility: Legacy .zcode.json paths are still checked

10.2 Persistence

All persistent state lives under ~/.deepseek-code/: 

~/.deepseek-code/
├── settings.json              API key, model, baseURL, defaultAgent, thinkingMode
└── sessions/
    ├── <timestamp-b36>-<r4>.json  Per-session message history + metadata
    └── ...                         (auto-pruned to 50 most recent)

Sessions are auto-saved on every message change via a useEffect in App.tsx. Session hashes use a combination of Date.now().toString(36) and a 4-character random string for uniqueness. Old sessions are pruned to keep the 50 most recent. Sessions can be resumed with --resume <hash> or the /resume in-app command.

11 MCP (Model Context Protocol) Support

Status: Partial Implementation. Configuration loading and TUI controls are fully implemented, but protocol-level tool execution through MCP is not yet active.

11.1 Implemented

  • MCP server definitions in .deepseek-code.json with command, args, cwd, env, and enabled flag
  • Runtime /mcp commands for listing, enabling, and disabling servers
  • MCP status indicators in the StatusBar and ShortcutOverlay
  • Runtime state management in App.tsx with enable/disable toggling

11.2 Architecture (Planned)

The planned MCP integration will introduce an MCPManager that starts/stops stdio MCP processes, pulls tool schemas from servers, converts them to the internal tool format at runtime, and routes tool calls through the manager with streaming result support. Server enabled/disabled state will be persisted to the session file.

  1. Add agent name to AgentName type in src/types/index.ts
  2. Add configuration in src/services/agent/index.ts AGENTS record
  3. The agent automatically appears in /agent and /help commands

12.4 Coding Conventions

  • Use Bun.file() over node:fs for new file operations
  • Export ESM with .js extensions in import paths (for Bun resolution)
  • Zod v4 + AI SDK v6 type inference issues handled with as any casts (intentional)
  • Each tool gets its own directory with separate prompt.ts
  • Prefer Edit over Write for modifying existing files

13 Current Limitations & Future Directions

13.1 Current Limitations

  • MCP tool execution: Configuration and UX exist, but protocol-level calls through MCP servers are not yet wired into the agent loop
  • AgentTool (sub-agents): Returns placeholder text; recursive agent calls not yet implemented
  • WebSearchTool: Stub implementation pending search API integration
  • No test framework: bun test will work once tests are configured
  • Single provider: Only DeepSeek (OpenAI-compatible) is currently supported; architecture is extensible via registerProviderAdapter()
  • Duplicate type files: src/core/types.ts and src/types/index.ts are nearly identical but not in sync
  • Legacy code: services/agent/base.ts Agent class and services/contextManager.ts are largely superseded by C++ native equivalents
  • Unused dependencies: chokidar is not used anywhere; ora is imported but the Spinner component uses its own implementation

13.2 Planned Enhancements

  • Full MCP protocol integration with dynamic tool discovery and lifecycle management
  • Custom agent definitions via config file (user-defined personas)
  • Inter-agent communication and handoff protocols
  • Agent-specific temperature and model configuration
  • Additional AI provider support (OpenAI, Anthropic, etc.)
  • Enhanced collaboration workflows with multi-turn planning
  • Memory persistence across sessions with retrieval-augmented generation
  • Structured testing framework and CI pipeline

14 Conclusion

DeepSeek Code presents a well-architected, production-quality terminal-native AI coding agent that successfully integrates large language model capabilities into the developer's command-line environment. Its design reflects several notable engineering strengths:

Modular Architecture

The clean separation between provider adapters, agent orchestration, tool execution, and the TUI layer ensures each component has a single, well-defined responsibility. The adapter pattern for providers and the buildTool() factory for tools make the system extensible without modifying core infrastructure.

Performance-Critical C++ Engine

The decision to use a native C++ engine (ai-sdk-cpp) for the core agentic loop—rather than a JavaScript-based loop—offloads session management, memory injection, context compaction, and multi-step orchestrations to compiled code, while preserving TypeScript's expressiveness for tooling and UI.

Interactive Permission Model

The async tool bridge enables a permission system that is both secure and fluid. Users can approve, deny, or provide feedback on tool operations without breaking the agentic flow, and the system's layered security (agent rulesets → user prompts → session-level overrides) provides granular control.

Real-Time Streaming TUI

The combination of Ink's React-based rendering, an AsyncGenerator-based event stream, and yieldToRenderer() scheduling produces smooth, real-time terminal updates. The attention to UX detail—from the animated welcome screen to tool badge colors, diff previews, and the slash command picker—elevates the terminal experience significantly.

While certain features remain in development (full MCP integration, sub-agent spawning, additional providers), the current codebase provides a robust, usable AI coding assistant that demonstrates thoughtful architectural design and a commitment to terminal-first developer experiences.
